# 公開前のセキュリティ確認

2026-10-16、GitHubで公開する前に、リポジトリの全履歴と公開対象のファイルの点検と、コードの静的なセキュリティレビューを行いました。秘密の値を点検ログに出さない方針で行っています。

## 公開対象の点検

- **秘密情報**：Stripe・Anthropic・OpenAI・GitHub・AWS・Google・Slackのキー、JWT、秘密鍵の既知パターンを全コミットの差分に対して検索し、該当なし。パターン検索は未知の形式の秘密を完全に検出する保証ではないため、GitHubのSecret scanningとPush protectionも有効にしています。
- **環境変数**：`.env.example` のAPIキーとStripeのキーは空欄。`.env*` は `.env.example` 以外をgitignoreで除外。
- **コミットの作者**：全コミットがGitHubのnoreplyアドレス。
- **個人情報**：メールアドレスは `example` ドメインのみ。人物・会社名はすべて架空。
- **登録番号**：リポジトリ内の登録番号43件すべてを国税庁の[適格請求書発行事業者公表サイト](https://www.invoice-kohyo.nta.go.jp/)で照会し、登録された事業者が存在しないことを確認（2026-10-16時点）。42件は乱数で作った番号で、今後の登録で一致する可能性はゼロではありません。残る1件は検査数字の計算を確かめるために使っている国税庁自身の公表された法人番号です。実在の事業者の特定に使わないでください。
- **画像とPDFのメタデータ**：評価用のPDFは作成ソフト（Chromium / Skia）以外の情報を含まない。PNG・JPEG・WebP・GIFに撮影機器・位置情報・作成者の記録なし。ローカルのファイルパスの混入なし。
- **依存パッケージ**：`npm ci` 時の監査で既知の脆弱性0件。CIでは `npm audit signatures`（レジストリ署名の検証）と、本番依存の高リスク以上の脆弱性で失敗する監査を毎回実行します。

## レビューで見つけて直したこと

コードを実行しない静的レビュー（認証、CSRF、権限、アップロード、AI連携、Stripe、SQL、ヘッダー）で、XSS・SQLインジェクション・コマンドインジェクション・他組織のデータの参照は見つかりませんでした。次の点を直しています。

| 重さ | 内容                                                                                                                                                                                     | 対応                                                                                                                                    |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 高   | ログイン試行の制限を、X-Forwarded-Forの偽装、メールの前後の空白、並列リクエストの3通りですり抜けられた                                                                                   | アカウント単位と接続元単位の二段にし、メールを正規化してから、照合の前に数える。記録の件数に上限                                        |
| 中   | リクエスト本文を全部読んでから大きさを確かめていたため、巨大な本文でメモリを使い切らせられた                                                                                             | ストリームのまま読み、上限を超えた時点で打ち切る                                                                                        |
| 中   | プロキシの後ろではセッションcookieにSecureが付かないことがあった                                                                                                                         | 実運用モードは `APP_ORIGIN` を必須にし、httpsならSecure。HSTSを追加                                                                     |
| 中   | 公開デモに誰でも任意のファイルを置け、全員の一覧に表示された                                                                                                                             | 公開デモでは同梱サンプル以外を、PDFの解析より前に拒否                                                                                   |
| 中   | AIの読み取りを無制限に再実行でき、運用者のAI利用料を消費させられた                                                                                                                       | 1枚3回まで。DBのCHECK制約で強制し、並列でも超えない                                                                                     |
| 中   | Stripeの通知が順不同で届くと、解約後に古い「有効」の通知で有料プランに戻り得た                                                                                                           | プランを最後に変えたイベントより古いイベントは反映しない                                                                                |
| 低   | 同じ状態のままなら提出者などの列をSQLで書き換えられ、DBによる自己承認の禁止を迂回できた（アプリの経路からは到達不能）                                                                    | その列を持つ遷移でしか変えられないようトリガーで検査                                                                                    |
| 低   | Originが `null` などの不正な値だと500を返していた。プロキシの後ろでHostが書き換わる構成に弱い。Stripeの戻り先URLが内部のアドレスになり得た                                               | 不正なOriginは403。`Sec-Fetch-Site` も検査し、実運用モードでは `APP_ORIGIN` と完全一致。戻り先も `APP_ORIGIN` から作る                  |
| 低   | 公開デモの初期化を管理者以外も呼べた。実運用DBへ公開パスワードのデモアカウントを投入できた                                                                                               | 初期化は管理者のみ。デモデータの投入はローカルのDB以外では拒否（明示の指定時を除く）                                                    |
| 低   | 起動時の検査がテーブル所有者のロールでの接続を拒否していなかった。ファイル行を他組織の請求書に紐付けるポリシーの穴。出力バッチに外部キーがなかった                                       | 所有者での接続を拒否。ポリシーで同じ組織を検査。外部キーと同じ組織の検査を追加                                                          |
| 低   | CSP・Permissions-Policy・COOPがなく、`X-Powered-By` を返していた                                                                                                                         | 追加（[脅威と対策](security.md)）                                                                                                       |
| 情報 | ドキュメントが「`app_user` はパスワードハッシュを読めない」と書いていたが、ログイン用のSECURITY DEFINER関数経由では受け取れる。存在しないスクリプトを指す `npm run extract` が残っていた | 記述を正確にし（[RLSの守備範囲](security.md#rlsの守備範囲)）、スクリプトを削除。デプロイ時に `eval/cases.json` が同梱されない設定も修正 |

残っている制約（PDF解析のCPU時間、複数台でのログイン制限の共有、二重契約の防止など）は [脅威と対策の「対象外」](security.md#対象外) に書いています。

## GitHubの設定

Secret scanningとPush protection、Dependabotのアラートとセキュリティ更新、CodeQL（`security-extended`）、プルリクエストでの依存関係の審査、非公開の脆弱性報告、`main` の強制プッシュと削除の禁止。GitHub Actionsは全アクションをコミットSHAで固定し、既定の権限を空にしてジョブごとに最小限を付与、チェックアウトの認証情報を残しません。

## 公開しているサンプル値

`.env.example`、`docker-compose.yml`、`db/local-roles.sql` には、ローカルのPostgreSQL用のユーザー名とパスワード（`*_local_only`）があります。秘密ではなく公開前提の開発用の値で、DBのポートは `127.0.0.1` にだけ公開します。**本番・共有環境では使わないでください。** 公開デモのログイン用パスワードも同じく公開前提です。

## 公開ソースと公開サービスは別

これはコードをGitHubで公開するための確認で、実運用サービスとしての安全性評価ではありません。実データを扱う前に、認証基盤（MFA・SSO・パスワードリセット）、複数台で共有するログイン試行制限、ウイルススキャン、バックアップ、電子帳簿保存法への対応、AIへのデータ送信の社内承認が別途必要です（[導入前に決める条件](freelance-submission.md#導入前に決める条件)）。
