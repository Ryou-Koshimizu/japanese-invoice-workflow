# 脅威と対策

| 脅威                                           | 対策                                                                                                                                                                                                                                                                                           | 確認方法                                                                                      |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 他組織のデータ参照・書き込み                   | 全リクエストを `app_user` ロールで実行し、RLSで `org_id` を強制。組織IDを偽装しても書き込めない。ファイルは同じ組織の請求書にしか紐付けられない                                                                                                                                                | `tests/database.test.ts`、`tests/postgres.test.ts`（実PostgreSQL）                            |
| 役割を超えた操作・自己承認                     | アプリの `can()` に加え、DBトリガーが遷移・役割・提出者を検査。提出者・承認者・出力バッチ・差し戻し理由などの列は、その列を持つ遷移でしか変えられない（承認者が自分の依頼の提出者を書き換えてから承認する経路を塞ぐ）                                                                          | 承認者が自分の依頼をSQLで直接承認しようとしても、提出者を書き換えようとしても拒否されるテスト |
| 出力済み請求書の改変（二重計上・改ざん）       | 出力済みは更新不可（トリガー）。DELETE権限なし。出力バッチは外部キーと同じ組織であることを検査                                                                                                                                                                                                 | テスト                                                                                        |
| 監査ログの改ざん                               | トリガーのみが書き込み、`app_user` にUPDATE・DELETE権限なし                                                                                                                                                                                                                                    | テスト                                                                                        |
| パスワード・セッションの漏えい                 | scryptでハッシュ化。`app_user` は `password_hash` 列と `sessions` 表を直接読めず、ログインに必要なSECURITY DEFINER関数（`search_path` 固定）経由でだけ扱う。セッショントークンはSHA-256で保存。cookieはhttpOnly・SameSite=Lax、実運用モードでは `APP_ORIGIN` がhttpsならSecure                 | テスト（開発中にこの権限の漏れを発見して修正）                                                |
| パスワード総当たり                             | アカウント単位（5回）と接続元単位（20回）で5分止める。試行は照合の前に数えるため、並列リクエストでもすり抜けられない。メールは空白と大文字小文字を正規化してから数える。未登録メールでも同じ時間がかかるようにダミーのハッシュ計算を行う。公開デモはパスワードを公開しているため接続元単位のみ | 実装（プロセス内メモリのため複数台では共有されない）                                          |
| CSRF                                           | SameSite=Lax cookie。状態を変えるAPIは `Sec-Fetch-Site` と `Origin` を検査し、実運用モードでは `APP_ORIGIN` と完全一致を要求                                                                                                                                                                   | E2E（別Originからの出力要求が403）                                                            |
| 不正なファイル                                 | 拡張子やContent-Typeではなく先頭バイトで判定。10MB・20ページまで。PDFの読み込み失敗は拒否。配信はnosniffで、PDF・PNG・JPEG以外の形式では返さない                                                                                                                                               | 実装                                                                                          |
| 巨大なリクエストによるメモリ枯渇               | 本文はストリームのまま読み、上限（ログイン2KB、JSON 200KB、Webhook 500KB、アップロード11MB）を超えた時点で打ち切る                                                                                                                                                                             | 実装                                                                                          |
| 公開デモへの任意ファイルの投稿                 | 公開デモでは同梱の架空サンプル（SHA-256で照合）以外のアップロードを、PDFの解析より前に拒否。デモの初期化は管理者のみ                                                                                                                                                                           | 実装                                                                                          |
| AI利用料の乱用                                 | AIの呼び出しは1枚につき9回まで（1回の読み取りで2〜3回、再試行と読み比べを含む）。呼び出しの前に短いトランザクションで回数を数え、DBのCHECK制約が上限を強制するため並列でも超えない。再試行するのは決まったエラーコードだけ。アップロード枚数は月のプラン上限をトリガーで強制                   | テスト（12並列で9回だけ成功、読み比べの3回目まで数える、SQLで回数を戻せない）                 |
| CSVによる数式実行                              | `=` `+` `-` `@` タブ・CRで始まる文字列セルの先頭に `'` を付ける                                                                                                                                                                                                                                | `tests/core.test.ts`                                                                          |
| AIによる値の捏造                               | AIは抽出のみ。検証は決定的なルール。PDFの文字情報に値が存在するかを照合                                                                                                                                                                                                                        | `tests/core.test.ts`                                                                          |
| 請求書内の文章によるプロンプトインジェクション | 文書はデータとして扱うよう指示。AIは抽出結果を返すだけで、ツール実行やDB操作の権限を持たない。出力はスキーマと長さで検証                                                                                                                                                                       | 構造上の制約（Codexはツール無効の読み取り専用サンドボックス、環境変数は許可したものだけ渡す） |

| RLSを迂回できる接続                            | 実運用モードの起動時に、接続ロールがスーパーユーザー・BYPASSRLS・テーブルの所有者でないこと、`app_user` のメンバーであることを検査                                                                                                                                                             | 実装                                                                                          |
| ブラウザ側の攻撃面                             | CSP（外部スクリプト・プラグイン・埋め込み・他サイトからのフレーム表示を禁止）、HSTS、Permissions-Policy、COOP、CORP、`X-Frame-Options: DENY`、`X-Powered-By` なし                                                                                                                              | `next.config.ts`                                                                              |

## RLSの守備範囲

RLSとトリガーは、アプリのコードの誤り（権限チェックの書き忘れ、IDの取り違え）から組織の分離と承認フローを守るためのものです。`app_user` として任意のSQLを実行できる者は、リクエストの文脈（`app.user_id` / `app.org_id`）を自分で設定でき、ログインや課金に必要なSECURITY DEFINER関数も呼べます。DB接続情報そのものは秘密として管理してください。

## 運用と組み合わせて守るもの

導入時に、次を前段のサービスや運用で受け持ちます。

- SSO、パスワードリセット、多要素認証（認証基盤）
- 複数台構成でのログイン試行制限の共有、大量のリクエストによるDoS（前段のプロキシやWAF）
- ウイルススキャン（保存前のスキャンサービス）
- PDF解析のCPU時間の制限（解析はメインスレッドで行う。公開デモでは同梱サンプル以外を解析前に拒否し、実運用モードでアップロードできるのはログインした組織のメンバー）
- 2つのタブで同時に決済画面を開いた場合の二重契約の整理（Stripeの管理画面で解約）
- 電子帳簿保存法の要件（タイムスタンプ等、保存サービス）
