# 請求書AIワークフロー — 提出用説明

## 何を解決するか

対象は、毎月数十〜数百枚の請求書を受け取る中小企業の経理担当者です。PDFや画像から取引先・金額・税額・登録番号を転記し、インボイス制度の記載事項と計算を目で確かめ、上長の承認を経て会計ソフトへ仕訳を入れる作業を想定しています。

このリポジトリは、AIの読み取り → 決定的なルールによる検証 → 人の確認 → 承認 → 仕訳CSV出力までを、権限・監査ログ・課金つきの業務システムとして示す技術デモです。

架空の会社と、このプロジェクトが生成した架空の請求書40枚で動作を示します。ChatGPT（Codex CLI、`gpt-6.1-sol`）で2回読み比べる方式により測定し、40枚すべてで必須項目が一致、誤りを仕込んだ6枚すべて検出（見逃し 0 / 6枚）、誤検出（正しい請求書を誤りと判定）0 / 34枚でした（2026-10-20、[検証記録](verification.md)）。実際の取引先の請求書では、導入時の受入試験で同じ採点を流して精度を確かめます。

## 2〜3分のライブデモ（APIキー・DB不要）

1. 公開デモ <https://japanese-invoice-workflow.vercel.app>（または手元で `npm run dev`）を開き、役割の選択画面を表示する。架空の「株式会社サンプル商事」の経理部であること、公開デモはAIを呼ばず正解データから作った読み取り結果を使うことを説明する。
2. **担当者**でログインし「株式会社アオバ通信」を開く。原本と読み取り結果が並び、税額と合計のエラーが強調され、エラーがあるうちは承認依頼できないことを見せる。
3. 10%の消費税額を正しい額に直して「保存して再検証」。検証のチェックがすべて付き、「AIの値から修正」の表示が付くことを確認し、承認を依頼する。
4. **承認者**で同じ請求書を承認する（承認のスタンプが押される）。担当者が自分の依頼を判断できないこと、差し戻しには理由が必須であることを補足する。
5. **管理者**で仕訳CSVを出力し、出力済みの請求書が編集できないこと、監査ログに修正・承認・出力が残っていることを見せる。

AIの値は2回の読み比べで確かめ、正しさはルールが判定し、人が原本と照らして直す設計であることを強調する。精度の説明には実AIの測定結果を使う。

## 実装として示せること

- **権限の権威はデータベース**：組織の分離は行レベルセキュリティ、承認フロー（遷移・役割・自己承認の禁止・出力後のロック）はトリガー、監査ログもトリガーが書く。アプリは全リクエストを制限ロールで実行し、起動時に接続ロールがRLSを迂回できないことを検査する。
- **AIは読むだけ**：抽出結果はZodで型検証し、検証は純粋関数のルール。PDFの文字情報に値が存在するかを照合し、AIの捏造を疑う。
- **2回読み比べる**：計算で確かめられない名称・番号・日付の読み違いに備え、2回独立に読んで食い違えば3回目の多数決。割れた項目は人の確認に回す（[ADR 005](adr/005-consensus-reading.md)）。
- **日本の実務**：登録番号の形式と検査数字、適格請求書の記載事項、税率ごとの端数処理の範囲、源泉徴収（10.21% / 20.42%）、重複の検出。
- **測れる品質**：正解付きの架空請求書40枚、項目別の採点、誤検出（正しい請求書を誤りと判定）と読み違いの見逃しの件数、モデル・コミット・データとプロンプトのハッシュを残す評価レポート。誤りを仕込んだ請求書をルールが検出できない場合、生成スクリプト自体が失敗する。
- **どの端末でも**：25種の画面の大きさ（折りたたみ端末・横向きスマホ〜4K）とChromium・WebKitで、はみ出し・文字の欠け・重なりがないことと、主な操作が最初の画面に収まることを自動テストで確認。全画面でaxeのWCAG 2.1 A/AA違反0件。
- **課金**：Stripe Checkoutと、署名検証・イベントIDで冪等なWebhook。月の処理枚数の上限はDBのトリガーで強制。
- **公開リポジトリとしての安全**：[SECURITY.md](../SECURITY.md)、[脅威と対策](security.md)、[公開前のセキュリティ確認](security-publication.md)。

## 導入前に決める条件

| 条件     | このデモ                                                                | 実導入前に必要なこと                                                     |
| -------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 請求書   | 架空の40枚・3種類のレイアウト                                           | 実際の取引先の請求書での受入試験、読めない様式の扱い                     |
| AI接続   | 本人のClaude APIキー、またはChatGPTログイン（Codex CLI）                | 利用契約とデータ送信の社内承認、機密区分、障害時の手入力                 |
| 精度     | 架空40枚で必須項目100%・誤検出 0 / 34枚（ChatGPT / Codex、2回読み比べ） | 実データでの項目別の精度と、人が確認する範囲の合意                       |
| 認証     | メールとパスワード。MFA・SSO・パスワードリセットなし                    | 認証基盤への置き換え（差し替え境界は `sessionFromToken()`）              |
| 保存     | ファイルはPostgreSQL内                                                  | 外部ストレージ、保存期間、タイムスタンプ等の法令対応                     |
| 会計連携 | 仕訳CSVの出力のみ                                                       | 対象の会計ソフトの取込形式、またはAPI連携                                |
| 運用     | ログイン試行の制限は1プロセスのメモリ内                                 | 複数台で共有する試行制限、監視、バックアップ、ウイルススキャン、障害対応 |

## レビュー時の再現方法

```sh
npm ci
npm run format:check && npm run typecheck && npm run build
npm run db:up && RUN_POSTGRES_TESTS=1 npm test
npx playwright install chromium webkit && npm run test:e2e
```

同じ手順をGitHub ActionsのCIが毎回実行します。実AIの評価は利用者自身のAPIキーまたはChatGPTログインで `npm run eval` を実行し、費用や利用枠は実行者に発生します。

## 面談で説明できること

このプロジェクトはAI支援で実装・検証しています。次の設計判断を自分の言葉で説明し、その場で変更を再現できます。

- 権限をアプリではなくDBで強制する理由と、ルールがTypeScriptとSQLの二か所にある代償。
- AIに計算させず、印字された値だけを読ませる理由（誤った請求書を「正しく直して」読むと誤りが消える）。
- 計算で確かめられない読み違いを、2回の読み比べで捕まえる理由と、その費用。
- 消費税の端数処理を「切捨て〜切上げの範囲」で判定する理由。
- 新しい検証ルールを1つ追加し、TypeScript・SQL・テストを揃える手順。
- Webhookで署名検証と冪等性が必要な理由。
