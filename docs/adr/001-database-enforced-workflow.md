# ADR 001：権限と承認フローをデータベースで強制する

## 判断

組織の分離はPostgreSQLの行レベルセキュリティ（RLS）、承認フロー（遷移・役割・自己承認の禁止・出力後の編集禁止）はトリガーで強制する。アプリの全リクエストは `asUser()` でトランザクション内に `SET LOCAL ROLE app_user` と `app.user_id` / `app.org_id` を設定してから実行する。アプリ側の `can()` は同じ規則で画面とエラーメッセージを作るためのもので、権威はDBにある。

監査ログはトリガーが書く。`app_user` には監査ログのUPDATE・DELETE権限がなく、請求書のDELETE権限もない。パスワードハッシュとセッションはSECURITY DEFINER関数経由でしか触れない。

## 理由

- 業務システムで一番高くつく不具合は「権限のすり抜け」。APIの実装漏れ一つで他社データが見える設計にしない。
- 監査ログをアプリが書くと、書き忘れる経路が必ずできる。

## 代償

- ルールがTypeScriptとSQLの二か所にある。片方だけ変えるとメッセージと実際の判定がずれるため、`AGENTS.md` で両方の変更とDBテストを義務づけた。
- PGlite（WASM）と実PostgreSQL 16の両方でテストしている。

## 実際に見つかった問題

DBテストを書いた時点で、`app_user` が `users.password_hash` を読めることが判明した（テーブル単位のSELECT権限だったため）。列単位の権限に変えて修正し、テストで固定した。
